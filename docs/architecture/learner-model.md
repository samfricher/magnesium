# Magnesium architecture

Magnesium keeps a private learner model in each workspace so lessons can build on earlier work. This guide is for runtime contributors; see the [user guide](../user-guide.md) for setup and [API reference](learner-model-contracts.md) for tool calls.

## From a lesson to lasting context

The host model teaches and interprets. Magnesium's Rust runtime handles persistence, evidence, workspace boundaries and controls, using the host's existing model and authentication. There is no separate model service or vector store.

```text
Host reads context ──► teaches ──► learner responds
        ▲                              │
        │                     capture original input
        │                              │
        └── current memories ◄── interpret and commit
                                     │
                           observations + checkpoint

Workspace sources ──► separate source search/inspection ──► host
```

Original input is captured before optional interpretation. One transaction saves observations, memory changes, the checkpoint, review updates and a successful request receipt. Failed interpretation leaves captured input available without a partially updated profile.

## What is stored

| Location | Purpose |
|---|---|
| `.magnesium/state.sqlite` | Canonical learner events, observations, current memories, history, sessions and receipts, one row per marked answer in `attempts`, the practice items (quick checks and gap-log rows) with what happened to each, and each kind of problem's help level |
| `.magnesium/backups/` | The copy of the learner store made before it was upgraded from schema 2, 3 or 4, kept as the way back, and in `gap-logs/` each gap log as it was brought in or before a hand edit was written over |
| `.magnesium/index/source-search.sqlite` | Rebuildable search cache for subject files; separate from learner memory |
| Search indexes | Derived from stored state; never new evidence about the learner |
| `.magnesium/sittings.sqlite` | Sittings, the quick checks each took, and what became of each. Before schema 4 it also held the quick checks; they move to the learner store the first time this runtime opens it |
| `Study/<plan>/gap-log.md` | The learner's page of a plan's gap-log rows. The runtime writes its Gaps table from the learner store after each change; the tutor writes Scores and Stretch items. The original of a log brought in, and any Gaps table edited by hand, are saved in `.magnesium/backups/gap-logs/` |
| `.magnesium/sittings.log` | One JSON line per sitting, rewritten from `sittings.sqlite`: what was due, posed, answered, declined, passed or failed, and how many more checks were due than the sitting took |

Learner payloads use `learner-model/v2` and database schema 5. The [SQL schema](../../src/learner/schema.sql), the [tables schema 3 added](../../src/learner/schema_v3.sql), the [tables and columns schema 4 added](../../src/learner/schema_v4.sql) and [those schema 5 added](../../src/learner/schema_v5.sql) define the fresh learner database.

The first time this runtime opens a schema 2 store, from the last release, or a schema 3 or 4 store, made only by the main branch, it upgrades it in place, once. Under the store's write lock it copies the store to `.magnesium/backups/state-schema-<version>-<time>-<id>.sqlite`, checks the copy, then adds the tables of each later schema and raises the version in one transaction. If any step fails, the store stays as it was. The copy is a complete store of its version: to go back to the runtime that made it, put it in place of `state.sqlite`. Other versions are preserved and refused.

Schema 3 adds the tables for issues #29, #30 and #31 at once, so a study folder is upgraded one time. `attempts` holds one row per marked answer: the question or which paper and question, a link to the observation and to the learner's own message, the mark (with marks out of marks on a paper), when, the time taken where a clock ran, the help given, the confidence letter, the skill it tests and whether it was cold. A helped answer is never stored as cold, and neither is a later answer on a label that already has one earlier the same day. `anchors` stays empty. `magnesium attempts` lists every answer, and `--json` prints the rows.

Schema 4 makes `practice_items` again (it was empty in every store) for #30. A practice item is something the learner got wrong, to be reproduced cold on later days: a quick check from chat or a gap-log row from a paper. `practice_events` lists what happened to each, in order: made by an attempt, repaired by the tutor, or answered again by an attempt. One attempt can count for several items. No pass, status or date is stored. The runtime works them out from the events, the attempts they name and the plan's test date, the When row of its Facts table. The rule is the papers stage's: three cold passes on three different days, the first at least a day after the repair, then at least 3 and 7 days apart, sooner to fit before the test, never below a day. A due redo that is not a pass fails a gap-log row, which waits for a new repair. A quick check's miss restarts it for the next day. An item brought in from a gap log or the earlier quick-check store starts from the state it had there. `gap_logs` records each plan whose gap log the runtime has taken over, and a hash of the Gaps table it last wrote, so a hand edit is noticed. `attempt_corrections` keeps an attempt as it was before the tutor corrected it. `attempts.slow` marks a right answer over the time allowed, which never passes a type S row. `attempts.item_id` from schema 3 is not used.

Schema 5 makes `help_levels` again (it was empty in every store) for #31, and adds `attempts.kind_key`, `attempts.no_start` and `imported_readings`. A kind of problem is problems that share one method; with a course graph it is a tag. The tutor names the kind on an attempt and says when the learner had no starting move on a new problem. The runtime keeps the teaching policy's ladder: after each attempt of a kind is stored or corrected, it replays the kind's attempts in order from the kind's base step. No starting move steps it forward, from none to a full worked example, a partly worked one, then the problem alone. A first try that is not right without help steps it back one; a decline does neither. The upgrade to schema 5 reads each "example step (KIND): …" phrase in an active memory once as a kind's base step, keeping the step with less help when two memories name one kind. It reads each memory's stated reading once too, such as "sound from MockA Q3", into `imported_readings` under each of its topics, keeping only sound and conditional.

A plan tag's reading is never stored. [`readings.rs`](../../src/readings.rs) works it out each time from the plan's gap-log rows, the attempts labelled with the tag, `imported_readings` and the plan's `graph.yaml`: open with a row at open; conditional with a row at 1 or 2 of 3, an open tag in key_need, an open tag in needs under a cold pass, or only a slow, partly right, helped or not-cold answer; sound with a cold, unaided, full, in-time answer on the tag, a closed row, or a pass reaching it through contains, with nothing in needs open; otherwise untested. A `graph.yaml` it cannot read is named in the result with its line, and the readings then use the rows and attempts alone.

Progress is never stored either. [`progress.rs`](../../src/progress.rs) works it out each time, and `magnesium progress` prints it, with `--json` for a study window. A pass is one right, unaided, cold, in-time answer on its own day, and three passes prove a skill. A skill with a practice item has the item's passes, and with several items the fewest. A skill with no item was never got wrong: its passes are the days with such an answer labelled with it, counted since its last wrong or partly right answer. A plan's skills are its graph's tags and its rows' labels. Every other label with an item or an answer is a skill in no plan. A plan's level, from 1 to 10, is the share of the passes earned over the plan's own skills: a graph is a fixed whole, so the level cannot fall when the learner starts something new. Each skill counts at the most passes it has held at one time, `best_passes`, worked out from its events and answers, so a miss never lowers the level or raises `to_next`. With several items that is the most the weakest item held, among the items made by then. A skill whose first item was made by a miss keeps the passes its answers held before. The plan's `passes` and each skill's `passes` stay what the skill holds now, and `level_passes` is the sum the level is worked out from. A chat attempt whose label names a graph tag, case, spaces, hyphens and underscores aside, is stored under the tag. Skills in no plan are counted as proven and in progress, and get no level. The command also prints how many redos and quick checks are due, and the days with an answer that was not declined. With `--json`, `today_counts` gives four counts for the local day, over the whole study folder, with or without a plan: `answered`, the answers given today that were not declined; `started`, the skills whose first such answer was today; `passes`, the passes earned today on checks, redos and skills with no item; and `due_tomorrow`, the open checks and redos whose next date is tomorrow. The top-level `today` stays the date. A runtime before this one prints no `today_counts`. Like the digest it never upgrades a folder. For a plan whose gap log is still a file the runtime has not taken over, it prints `"from": "file"` and no skills, since those rows are not in the record yet.

A memory describes strengths, difficulties, assistance and uncertainty rather than a mastery score. Observation references connect it to original events; history retains earlier descriptions and reasons for change. New observations can correct an interpretation while preserving relevant earlier work.

A session holds the problem, working diagnosis and next step. Its checkpoint records the memory revisions used. Planned tasks stay in planning text until a proposal event exists. Reading or dismissing a review suggestion does not establish performance.

## Consistency and control

Reads use bounded SQLite snapshots. Small collections return a complete compact directory; larger ones use lexical retrieval and whole-record paging. Search cues are not evidence. Dirty indexes leave browsing, direct reads and literal matching available; `magnesium memory reindex` rebuilds them.

Writes check expected revisions. Identical successful retries return the saved receipt; competing edits require rereading and reconciliation. Cancellation can leave raw input pending, and a lost response cannot undo an already committed update.

A sitting begins with the first learner message after three hours without one. A prompt hook notes the time of each message in a conversation that records, never its text. A host without one counts a committed update that carries learner input. An `attempt` on an observation is stored as a row of `attempts`, and in the same transaction a chat attempt makes or answers the quick check on its label. A wrong or partly right first try, an "I don't know" (declined), a right one reached only through a full solution, or a request for the full solution before any answer, makes or restarts one check per label, due the next day. A right one reached with a hint or a step makes one, or brings a check that is not yet due to the next day and keeps its passes. A right, unaided first try on a label that has no item, open or closed, and no earlier answer, makes one check too, so the skill comes back and can earn its passes. When that answer is also cold and in time, the check keeps it as its first pass and is due 3 days later. Otherwise it holds no pass and is due the next day. A second right answer, a right answer on a skill that has an item, and a right answer to a due check make nothing new. On a due check, a right answer with any help earns no pass, and a decline is free. A right, cold, unaided first try on a due check passes it, and it returns after 3 and then 7 days. The third pass, on a third day, closes it. A paper attempt with `gap` makes a gap-log row, and an attempt with `counts_for` redoes the rows it names. After the update commits, the runtime brings in any gap log it has not taken over and writes each plan's Gaps table. A sitting takes up to three due checks: first those a miss, a decline or help made or has touched, then those a right first answer made, each group the longest due first, as `due_checks` in [`practice.rs`](../../src/practice.rs) orders them. The first tool result of a sitting carries a `sitting_opener` with those checks and the paper redos due, each with its stored next question. Every turn's notice gives the counts until each check is posed or declined. In Claude Code, a reply that says "Quick check n" poses check n, and so does an answer or a decline. The end-of-turn hook records the delivered reply. In a session the study window starts, which it marks with `MAGNESIUM_SURFACE=window`, the tool server also offers `reply`: the tutor sends its whole reply through it, the window draws the call's input as it streams, and the runtime records the delivery from that call, keyed by the learner message it answers, and spots a posed check in it. The end-of-turn hook then records only text the tutor wrote besides it, so a reply is kept once. A committed update whose attempts name a kind returns `help_levels`, and the result of a papers or papers-loop instruction load, of an update that touches a plan's practice, and of a session start or resume whose goal names a plan returns that plan's `readings`. The result of a session start or resume also lists, as `earlier_answers`, up to eight of the learner's latest answers whose label or kind shares with the goal a word of four letters or more that names a topic (common words such as "what" and "with" are left out), so a new conversation knows the topic is not new without a search. These facts schedule practice and choose help only. The observations are the evidence.

Pause, stop and recording controls apply to the current host/thread independently of interpretation; pausing or completing the lesson itself stops every conversation sharing it. Recording-on does not resume a lesson. Recording-off blocks new learner text in semantic records and context receipts, leaving existing data and provider conversations intact. A context receipt records packet preparation, not delivery or attention.

Source access checks scope, exclusions and file versions independently. Extraction happens outside the writer lock; revision checks prevent stale results from being published. A search indexes only what fits its own budget. After it returns, the MCP server keeps indexing the folder on one background thread until nothing is left, and stops that work when the host disconnects. Export-marked private trees stay excluded from source discovery and inspection, including after copying or renaming.
